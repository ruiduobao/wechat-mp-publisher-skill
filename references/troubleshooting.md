# 故障排查与恢复

先定位失败阶段，再决定是重试、补配置还是停止。不要通过清历史、另建副本、直接改正文 DOM 或放宽验收让任务显示成功。

| 提示或现象 | 先核对 | 恢复动作 |
|---|---|---|
| `needs-title` | 新文是否缺15字以内语义外题；映射键是否为 articleId | 合并私有标题映射，再预检；不改源文完整原题 |
| TypeScript 失败 | 当前源码和锁文件是否匹配；依赖是否安装 | 修复错误并复查，启动器不绕过检查 |
| 运行中的专用浏览器未找到 | Profile、实际进程命令行和调试端口 | 恢复用户选定的专用浏览器；不杀其它 Edge |
| 浏览器连接成功但主页不就绪 | 是否需要重新登录或平台加载异常 | 报告需要续期，不反复弹扫码图片 |
| 模型服务 403 / 子 agent 不能启动 | 模型服务是否拒绝、是否实际执行过工具 | 记录独立测试未执行；不能归因公众号登录 |
| `unsupported-message-type` | 是否为图片轮播、正文祖先是否隐藏 | 保留 ID；单独核对同篇真实普通长文，不改 CSS 或隐藏类型 |
| `needs-content-refresh` | 重复 H1、H1 包裹正文、原稿图片缺失 | 确认干净源文后，在原 ID 完整重建 |
| 缺图、源文件仍在写入 | 本地引用路径、大小/mtime稳定性 | 等同步完成或修正来源；保留映射 |
| 历史、封面或标题 JSON 损坏 | 实际错误文件及原始数据 | 保留原文件与备份后修复，不当空字典覆盖 |
| 图片定位失败、残余占位符 | 原生输入是否替换了选中的准确文本 | 停止保存；修正选区同步与输入，不能直接删文字节点 |
| 图片已上传但检测不到 | 图片是否位于标记段落或紧邻独立图片块 | 定位正确位置；不能使用全局最后一张图兜底 |
| 仅图库条目数没有增加 | 微信可能复用了同一素材 | 按本次文件名和素材身份核对，不强求新增条目 |
| 裁剪确认后没有封面 | 活动弹窗、确认按钮是否启用、是否只派发一次点击序列 | 等弹窗真正关闭，再检查封面实际 URL |
| 名片看得见但复验失败 | 是否真正 mp-common-profile、账号是否正确、其后是否有正文 | 用真实原生模板或官方工具栏修复，不插仿制 div |
| 保存超时 | 回包、URL新分配ID、草稿是否已自动保存 | 独立重开确认文章身份并保全ID，再决定重试 |
| 保存成功但重开不一致 | ID、正文文字、图片、封面和名片各项结果 | 保持 saved-unverified，在同一 ID 修复，不标完成 |
| 图片地址从 `/0` 改为 `/640` | 是否同一合法 qpic 素材，其它路径和参数是否相同 | 按素材身份比较，继续核对顺序和真实加载 |
| 进程锁占用 | 对应 PID 是否仍工作 | 等现有任务结束；不直接删活锁启动第二个写进程 |

## 图片占位符修复的边界

先精确建立正文选区，等待编辑器同步选区，再通过原生输入替换为本次标记。替换完成要同时检查标记存在、原占位符已消失。只检查“标记出现”可能把光标旁插入当成真正替换。

如果原占位符还在，应该停止该篇并保留证据。给 `textContent` 直接赋值会绕过微信编辑器模型，可能临时看似干净，后续重绘或保存又恢复。编辑器状态、DOM 和服务端草稿的一致性必须靠原生输入及独立重开验证。

同一文件在正文中引用多次时，每次出现都使用独立占位符。不能因为相同图片已经出现过，就复用其它位置的“上传成功”结论。

## 保存后失败与自动保存

拿到保存 ID 后先落盘为未验收。微信可能在手动保存前生成 ID；失败重跑前先从服务器读回该 ID 并核对正文身份。不要因为主日志缺少“保存成功”就断定没有草稿。

已存在的错误或重复副本不要自动删除。记录其来源与正式映射，清理属于另一项操作。报告中区分“没有提交手动保存”和“微信绝对没有自动保存”。

## 旧基线与缺映射

旧文章缺少确认映射时，应按真实正文、论文标题、配图和消息类型核对候选。标题相似、摘要相似、数字 ID 接近都不能单独建立映射。保留旧候选证据，在持锁状态下更新经核实映射。

## 还原代码与保全资产

回退代码不能覆盖新状态库。已生成的 appmsgid 是远端资产引用，必须保留。修改程序后重新做类型检查、受影响回归和授权真实草稿测试；具体步骤见 [testing.md](testing.md)。
