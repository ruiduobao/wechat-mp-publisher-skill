# 事故复盘与长期规则（2026-11-13 ~ 2026-11-22）

本文回答两个问题：这段时间为什么反复返工？以后用什么硬规则避免同样的成本？
证据来源：`git log` 的修复提交、私有 `content-corrections.json`、`keepalive-history.jsonl`、各批次发布日志与当轮会话记录。结论只写可复现或可追溯到日志的部分；无法归因的明确标注“未证实”。

## 二、七个共同根因

**R1 用代理指标代替真实路径。**
Cookie 存在 ≠ 服务端可用；HTTP 200 ≠ 页面已登录；fetch 成功 ≠ 用户能打开后台；`saved-unverified` ≠ 失败；DOI 可解析 ≠ 是本文主 DOI。
凡是要下结论，必须走用户真正走的那条路：真实导航、真实保存、独立重开、官方元数据。

**R2 把一次观测写成长期承诺。**
“96 小时”“一个月”“扫一次就行”都来自单次样本。平台 TTL、反爬策略、CDN 重签名都会变。
只描述“当前实测 + 平台控制 + 不承诺”，并把不确定性写进输出状态（healthy/needs-qr/unknown）。

**R3 对字符串与 DOM 的边界做隐式假设。**
`WECHATIMGPH_1` 是 `WECHATIMGPH_10` 的前缀；`textContent` 会把相邻块直接拼接；图注以年份开头；绝对路径会进入指纹；URL 会被全角括号截断；Markdown 标题长度按字节/字符/码点算结果不同。
凡是匹配标识符，按语法单元（文本节点、正则边界、码点）处理；凡是派生键，先归一化环境差异。

**R4 环境与生命周期没有纳入契约。**
系统代理、浏览器是否运行、调试端口是否还活着、Profile 是否被占用、Windows 引号/路径/编码，都会改变结果。
启动器必须把这些当成输入：本地回环绕代理、端口就绪轮询、卡死自愈、路径归一化、原子写 JSON。

**R5 修复没有回写成检测或规则。**
同类的“假阴性/误拦截/半批停下”反复出现，是因为修完就当结束。
每个修复至少留下一个：回归测试、诊断命令、preflight 检查、遥测字段或排障文档；否则下一轮仍靠人肉记忆。

**R6 资源耗尽没有纳入预检。**
磁盘写满会连锁触发同步失败、页面资源加载失败、重开复验 JS 异常，表现像“内容/编辑器问题”，实际是环境问题。
凡是长跑自动化，启动前检查磁盘/临时目录空间；缓存与临时文件外置到有空间的盘；把资源指标纳入巡检报告。

**R7 平台 TTL 与客户端能力被混为一谈。**
Cookie `Max-Age=96h`，打开官方根路径会刷新为“当前+96h”，所以保活能滑动 TTL；但服务端仍可随时撤销会话（并行登录、风控）。
用工具测量（`session-expiry.mjs`），不要猜；把“能滑动的”和“不能控制的”分开写进文档，避免反复调参。

## 三、硬规则（写进日常流程）

- **P1 真实路径优先**：登录看真实导航后的页面状态；保存看独立重开；论文看官方元数据；不要把中间信号当结论。
- **P2 三态输出**：`healthy / needs-qr / unknown` 各自对应“继续 / 人工扫码 / 可重试”，绝不把不确定说成确定。
- **P3 不承诺平台期限**：只写“由平台控制”，需要时给实测值与观测时间。
- **P4 登录只在专用 Profile**：任何其它浏览器/设备登录同一账号都可能顶掉自动化会话；扫码必须发生在专用窗口。
- **P5 本地回环永不走代理**：启动器强制 `NO_PROXY=127.0.0.1,localhost,::1`；CDP 先轮询就绪，卡死只重启专用 Profile。
- **P6 标识符按边界匹配**：占位符、DOI、URL、标题长度都按语法边界与码点处理；禁止全局 `indexOf` + 前缀猜测。
- **P7 派生状态只经工具改**：短标题用 `bun run titles`；内容修正用 `private-json.mjs`；禁止内联 `node -e`/heredoc 拼 JSON。
- **P8 写入前一次性 preflight**：全部新文外题、真实性、图片完整性、锁与队列一次校验；不合格在“写第一笔之前”停止。
- **P9 失败要可执行**：`fail / warn / skip / needs-title / needs-cover / needs-attention / unknown` 各有明确动作，禁止只打印一句“失败”。
- **P10 文档随代码同提交**：删除无法复现的承诺；改了语义就同时改 SKILL/operations，避免下一轮按旧文档操作。
- **P11 一修一测一诊断**：每个修复配回归测试或可重复诊断命令（如 `WECHAT_DEBUG_PLACEHOLDER=1`、`keepalive-report.mjs`、`verify-doi-official.mjs`）。
- **P12 先看时间线再下结论**：排障先跑 `keepalive-report.mjs` 与最近发布日志，确认是“真掉线 / 误报 / 环境故障”，再决定动作。
- **P13 资源预检**：启动前检查仓库盘与临时盘空间（默认 300MB 安全线）；浏览器缓存与临时图片外置到大容量盘；磁盘不足时明确停止，不写半批。
- **P14 瞬时错误与内容错误分开**：封面/CDN/页面加载超时自动重试一次；内容、标题、核查错误绝不重试。
- **P15 平台 TTL 只测不猜**：用 `session-expiry.mjs` 报告剩余小时；不承诺天数，不自动续期，不绕过人工扫码。
- **P16 巡检报告固定四项**：登录态、会话剩余小时、磁盘剩余、待处理篇数；缺一项就不算完整巡检。
- **P17 外部链接批量预检**：GitHub/DOI/X 链接逐条核验；死链不进草稿，修正只经 `private-json.mjs` 登记，不手改源文件。
- **P18 新故障必须留下观测手段**：每次修复至少新增一条遥测字段、诊断命令或回归测试，否则视为未完成。

## 四、发布前检查清单（照做即可）

1. `sync-from-github.mjs` 成功且提交号已记录；失败不当作“没有新文”。
2. `--keepalive` 为 `healthy`；`needs-qr` 停；`unknown` 先跑 `keepalive-report.mjs` 与端口/代理检查，不写稿。
3. `--check --verify`：FAIL 拦截；WARN 必须有官网二次核验记录（`verify-doi-official.mjs` 或出版社/arXiv 页面）。
4. 所有新文短标题已合并（≤15 码点，语义化，不机械截断）。
5. 缺图/缺封面先处理，不往正文塞图凑封面。
6. 写入后逐篇独立新标签复验 8 项；`saved-unverified` 只是中间态。
7. 最后 `--check` 确认未入库新篇为 0；报告新增/更新/跳过/待核对/失败。

## 五、成本排序（先修什么）

1. **会话探测与浏览器生命周期**（R1/R4）：一次误判会阻塞整批稿，且最容易反复。
2. **占位符/空段/标题等编辑器边界**（R3）：一次失败会让单篇返工 2~3 轮。
3. **DOI/链接二次核验**（R1）：每批都可能遇到，手工排查成本高。
4. **私有 JSON/状态编辑**（R3/R5）：出错会污染状态库，恢复成本最高。

新问题若落在这四类，默认按“先修根因 + 加检测 + 写文档”处理，不接受只改一次现场。
